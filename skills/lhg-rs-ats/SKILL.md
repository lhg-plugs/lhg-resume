# lhg-rs-ats：ATS 诊断五步法

> 目标：让简历先过机器那一关。现实是：大公司第一轮看你简历的不是人，
> 是 ATS（Applicant Tracking System）。格式稍有问题，解析出来就是乱码，
> 关键词对不上，直接进"已读不回"。
> 核心纪律：**先跑脚本（机器），再做判断（人）；blocker 不清零，不许说"可投递"。**

## 1. 何时使用

- 每次改完简历、投递前 → 跑全流程
- 换目标岗位 / 换 JD → 重新跑第 3 步（关键词部分）
- 只想快速看一眼 → 只跑第 2 步（脚本），10 秒出结果

## 2. 第一步：跑确定性审计脚本（必做，零成本）

在简历文件所在目录，用你所在平台执行本地脚本的方式运行：

```
python3 <插件目录>/scripts/audit/resume_audit.py --target <简历文件或目录> --jd <JD文件> --format text
```

- 脚本输出 JSON（含每条发现的行号、规则说明）与人类可读报告。
- 有 blocker 时脚本以非零 exit code 退出——这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`；想更严可设为 `warning`。
- `--jd` 可选；给了 JD 才会跑关键词覆盖率规则（RES-JD-001/002）。
- 脚本只做"机器可判定"的事：联系方式、日期格式、动词开头、量化数字、关键词覆盖。
  它判定不了"这个数字是不是真的""这段经历含金量如何"，那是第 5 步的事。

## 3. 第二步：ATS 兼容性五维检查

ATS 解析简历时最常见的翻车点，按致命程度排序：

### 3.1 关键词覆盖率（最重要）
- 从 JD 提取"硬技能词"（如 Python、SQL、用户增长、A/B 测试）与"软要求词"（如跨部门协作）。
- 简历中自然出现 ≥40% 的硬技能词为合格线；<40% 触发 RES-JD-001。
- 注意：**覆盖≠堆砌**。把关键词藏在"技能清单"里凑数，人工一看就穿帮；
  正确做法是把关键词嵌进经历 bullet 的动词+成果里。
- 同一关键词出现 ≥8 次触发 RES-JD-002（堆砌嫌疑），删到自然为止。

### 3.2 格式兼容性
- 单栏布局：双栏/三栏简历在很多 ATS 里会被读成乱序。不确定就用单栏。
- 不用表格、文本框、页眉页脚放关键信息：ATS 经常直接跳过这些。
- 不用图片、图标、进度条展示技能：机器读不到，"熟练度 90%" 的进度条 = 空白。
- 字体用系统常见字体；PDF 导出时确认文字可选（扫描版图片 PDF = 零分）。

### 3.3 章节完整性
- 三大件缺一不可：教育背景、工作经历、专业技能。缺一个触发 RES-SEC-001。
- 章节标题用标准词："工作经历"不要写成"职场生涯"，"教育背景"不要写成"求学之路"——
  ATS 靠标题关键词切分章节，花哨标题会被误判。

### 3.4 联系方式
- 手机号 + 邮箱是底线，缺一个都是 blocker（RES-PII-001）。
- 邮箱用正经邮箱；QQ 邮箱可以，但别用"葬爱家族"这类昵称。
- 隐私红线：**不要写身份证号、详细家庭住址**（精确到小区门牌那种），
  写了触发 RES-PII-002，必须删。城市名足够了。

### 3.5 日期一致性
- 全篇只用一种日期格式，如 `2021.06–2023.08` 或 `2021年6月–2023年8月`，混用触发 RES-FMT-001。
- 在职写"至今"或"Present"，不要留空让人猜。
- 时间倒序：最近的经历在最上面。

### 3.6 不同投递渠道的差异
- **公司官网/招聘系统**：ATS 最严格，按 3.1–3.5 全套检查，一字不差。
- **招聘 App 内投递**：部分 App 会重新解析 PDF，3.2 的格式要求同样适用。
- **猎头/内推**：先过人眼，ATS 权重下降，但关键词覆盖率仍影响猎头搜到你的概率——
  猎头也是用关键词在人才库里捞人的。
- **邮件直投**：标题写"姓名-应聘岗位-工作年限"，正文贴精简版经历，附件用规范命名的 PDF。
  附件命名见 lhg-rs-version 第 7 节。

## 4. 第三步：分级

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 投了也白投：缺联系方式、关键词覆盖率极低、格式机器不可读 | 必须修，不修不许投递 |
| warning | 大概率被刷：bullet 无动词、无量化、日期混用、关键词堆砌 | 本次改完；改不掉写理由进报告 |
| nit | 洁癖项：bullet 过长、超 2 页、标点中英混用 | 顺手修 |

## 5. 第四步：人工复核（脚本覆盖不到的）

- [ ] **数字真实性**：每个数字都能说出出处吗？说不出的标 [待确认]，**不许编**
- [ ] **关键词自然度**：遮住 JD 看简历，读起来像人话吗
- [ ] **一页纸测试**：打印预览，2 页以内吗？超了先砍"自我评价"空话
- [ ] **岗位针对性**：这份简历不看文件名，能猜出投的是什么岗吗
- [ ] **错别字**：全文通读一遍，公司名、人名、产品名零容忍

## 6. 第五步：输出诊断报告

报告模板：

```markdown
# ATS 诊断报告（日期 / 目标岗位）
## 结论：可投递 / 需修改
## blocker（n）：已修 n，剩余 n
- [规则ID] 行号 —— 说明 —— 状态（已修/需人工）
## warning（n）：已修 n，豁免 n（理由）
## nit（n）
## 关键词覆盖率：x%（JD 硬技能词命中 n/m）
## 人工复核：5 项中通过 x 项
## 需人工补充
- ...
```

报告存为 `resume-audit-YYYYMMDD.md`，下次换 JD 时对照回归。

## 7. 常见误区（反模式）

- ❌ "关键词越多越好"——堆砌被人工一眼识破，反而减分
- ❌ 用"精通/专家"形容所有技能——没有证据的副词都是空话
- ❌ 一份简历海投所有岗——每换一个 JD 就该跑一次诊断
- ❌ 为了过 ATS 把简历写成关键词清单——机器过了，人那关过不了
- ❌ 编数字让"量化检查"通过——**这是红线**，面试 3 分钟就穿帮，还可能进黑名单

## 8. 误报处理

1. **判断三问**：这行真的有问题吗？规则本意是什么？按规则改会破坏原意吗？
2. **确认误报**：在报告豁免清单里写清理由，不要悄悄改脚本。
3. **拿不准**：按 warning 处理，不要直接忽略。
4. **规则本身有问题**：附最小复现文本提 issue（见第 9 节），不要自己改阈值。

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本是否真的跑了（而不是"我觉得没问题"）？→ 没跑不算做。
2. blocker 是否清零或全部列入"需人工补充"？→ 有遗漏就补。
3. 人工复核 5 项是否逐项打勾？→ 打勾要有依据。
4. 有没有编造任何数字？→ 有一个就不许交付。

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，
确认坏 fixture（bad.md + jd.txt）的 blocker 全命中、好 fixture（good.md）零 blocker
（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-resume/issues，
正文写清"输入 → 错误输出 → 期望输出"。规则误报/漏报请附最小复现文本。
